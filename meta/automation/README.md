# 每日采集、核实与更新

截至 2026-10-22，既有“AI 软件变革资料每日采集与更新”任务每天北京时间 06:30 在自有云电脑运行，已配置为在资料处理后维护问题清单。任务定义由既有自动化管理；此说明记录仓库侧约定。首次自然运行待验证，不能将配置完成视为定时执行已跑通。

## 更新规则

- 遵守 `meta/policy.py` 中的收录政策与字段规范。
- 正式收录必须同时通过 `meta/policy.py` 的范围、证据和增量价值三道门；任一道不通过或无法判断，留在候选表，不进入正式目录。
- 评估来源时，按材料类型核对出品方的相关资质、作者专业背景、对内容的直接责任及方法、数据、代码和测试的可检查程度。权威性用于校准证据强度与主张边界，不得仅凭机构名头收录；厂商自述不能单独证明效果优越，个人或社区材料可由可检查实现、测试或可复现数据支撑。
- 每条新材料附简明、客观、可由原文核对的摘要；摘要说明对象、方法或覆盖范围，不加评价、推荐或推测。旧条目没有摘要的，定时任务逐步核实来源并补齐。
- 每条新材料填写“收录理由”，明确指出原文内容如何对应本仓收录范围及所选主题；理由必须能由一手来源核对，不写评价或推测。候选转为正式条目时，将核实后的理由写入 `meta/catalog.py`。
- 出品方按原文署名记录；仅在出处明确支持且有助识别时，在 `meta/catalog.py` 的 `BRAND_CONTEXT` 中补充“品牌；代表产品/项目”，不要从标题猜测关联。
- 以 `meta/catalog.py` 为正式资料源。先查一手来源核实内容、日期、作者/组织、原始链接及收录范围，再自动补充符合标准的资料。
- 每次采集单独核对最近 7 天的日期覆盖：查看 arXiv 分类最新列表、厂商和标准组织原站、GitHub 项目原仓，以及直接负责工程实践的个人或团队原文；对缺口日期做定向检索。搜索结果只用于发现，收录仍须逐条核实一手来源并通过三道门。
- 运行摘要分别报告最新正式条目的首发日期、最新审阅的一手材料日期及未收录原因；若两者相差，不把来源未发布、检索遗漏和证据不足混为一谈。不要为填补日期空档而降低准入门槛。
- `README.md` 和其他目录文件由 `python3 meta/build.py` 生成，不手工编辑。
- 核查证据不足或语义边界不清的资料只记录在 `meta/candidates.tsv`，并注明一手来源和待核实点；不得猜测后正式收录。
- 运行 `python3 meta/check.py` 与 `python3 meta/build.py` 并检查 diff；是否提交和推送以当前自动化任务的明确指令为准。
