# 问题探索维护

`meta/questions.json` 是唯一可编辑问题数据源，`questions.json` 由现有 `python3 meta/build.py` 生成，禁止手改。`meta/candidates.tsv` 只判断材料是否收录；问题池管理值得追问的疑点，不改变 `meta/policy.py` 的准入标准。

## 数据接口 v1

顶层 `schema_version: 1` 与 `questions` 数组。每项字段：

| 字段 | 约定 |
|---|---|
| id | 稳定编号 Q-0001 起，永久保留，不复用 |
| kind | 解释型（竞争性假设）或决策型（备选方案） |
| topics / tags | topics 复用 `meta/catalog.py` 的 TOPICS；tags 引用顶层受控 `tag_vocabulary` 的 ID，每项 1–5 个 |
| options | 候选答案／方案数组，格式见下方；待澄清可为空 |
| title / basis | 问法、发现依据；区分原文事实与推断 |
| sources | 原始来源数组：稳定 id、title、https url（优先章节锚点／固定代码行）、checked 核读日期、evidence 具体段落或证据边界 |
| value | 一句话研究价值 |
| known / unknown | 已知与尚未证实的内容分开 |
| next_step | 可执行的下一步查证 |
| status | 待澄清、待研究、已转研究、搁置 |
| updated | YYYY-MM-DD，等于历史末项日期 |
| history | 按日期升序记录 date、reason；解释新增、补证、改问法、状态变化原因 |
| merged_into | 未合并为 null；合并后保留原项与旧编号，填写目标编号，禁止循环或悬空 |

每项 `options` 包含稳定 `id`（如 A/B/C，在该问题内唯一、永久不复用）、`content`（实质候选内容）、`basis`（已知依据及推断边界）、`evidence_needed`（支持、反驳或比较该选项尚需查证的证据）、`conditions`（适用条件）及 `cost`（代价）。后两项未知时用 `null`，页面显示待查；其余字段不得空缺。改写选项须在问题历史中记明原因及旧 ID 的含义变化，不通过换 ID 隐藏修订；移除选项也保留历史去向。

待研究须有至少两个实质不同的候选解释或方案。程序检查编号、必填内容、重复内容和常见占位词；是否实质不同还须人工审查，不能用“其他／不知道”或改写同一方案凑数。尚未形成选项的问题留在待澄清，`options: []`，并在 `next_step` 说明如何形成和区分候选解释／方案。后续补齐并核对证据边界后，才进入待研究。

候选选项不是投票，也不预设唯一正确答案、互斥或穷尽；可组合，亦可能存在尚未发现的解释或方案。明确标注本项目提出的假设／方案与来源已陈述的事实；不把待核证据写成支持结论。Q-0001 的 A/B/C 是待评估方案，其中 C 需要另行设计人工或工具执行机制，不能解释成 GitHub AI Scan 原生可以阻止合并。“按风险组合采用”作为说明，避免与三个方案重叠凑选项。

“已转研究”表示进入研究过程，不表示解决；部分答案写入已知和未知，不直接标解决。合并时旧项设为搁置并记录去向及原因；网站保留旧项并显示链接。研究结果与证据先写入历史，问题没有可靠答案时继续保留未知。

## 每日采集后的独立步骤

截至 2026-10-22，既有“AI 软件变革资料每日采集与更新”任务已配置为在资料处理后维护问题清单；保持每天北京时间 06:30 在自有云电脑运行，仅在任务中汇报，不发送邮件。首次自然运行待验证，配置完成不代表定时执行已跑通。

1. 先完成材料采集和准入判断，再检查本次材料是否影响已有问题。
2. 新疑点先检索标题、来源与已知未知，必要时新增稳定编号，并明确问题类型、候选解释／方案、相关主题及受控议题标签；未形成选项先留待澄清并说明形成路径。重复问题只补证据与核读日期。
3. 修改问法或选项须记录原因；新来源只回答一部分时更新已知、未知、选项待核证据及下一步，不把已转研究视为答案已证实。
4. 无影响不改内容或更新时间，不空跑修订记录，不为数量补问题；不写企业私密信息。
5. 采集与问题更新分别报告：前者报告正式收录/候选及原因；后者报告新增、补证、修订、合并、搁置或无变化。
6. 运行构建、检查、单测和 diff 检查。是否提交与发布由当次授权决定。问题维护沿用既有每日采集任务，本说明修订不修改自动化定义。

## 可追溯引用

URL 只在问题的 `sources` 中维护一次，稳定来源 `id` 由同问题内的引用数组使用。`basis_refs` 对应发现依据，`known_refs` 对应已知事实，`next_step_refs` 对应下一步查证的明确目标。候选选项增加 `basis_refs`（提出依据及前提）、`evidence_refs`（已取得的支持证据）、`counter_refs`（已取得的反对证据）、`target_refs`（待核目标）。数组可空，页面会分别显示尚缺来源、支持／反对证据或待核目标，不能用前提来源冒充方案效果证据。

`checks` 仅记录已完成查证：稳定 id（V-001 起）、date、result、非空 `source_refs`。未开展查证时为 `[]`；未来行动只写下一步或选项待核证据，不写成已完成记录。链接优先描述性章节名称或固定 commit 的代码行。新增来源须真实核读，描述核读范围；仅有 URL 不等于可访问、支持事实或实验证明，静态校验也不能替代这些核验。

Q-0001 的发现依据链接到 GitHub 公告 How it works；C 的前提与待核目标链接到 GitHub 官方 Limitations。已核读它们对原生门禁的限制；尚无 A/B/C 效果的支持或反对证据，需另找公开实践与结果，不能从公告推出。

## 主题与议题标签

主题必须复用资料库现有七主题，不新增平行分类。问题至少关联一个相关主题；标签表达少量可复用的具体议题，不能拿状态、问题类型或已有主题当标签。顶层 `tag_vocabulary` 以稳定英文 ID 映射展示名称，问题 `tags` 只引用 ID，避免别名散乱；新增前先查词表，确认现有标签不适用且有复用价值，再新增并记录原因。禁止空白、重复、未知标签，每项最多五个。

当前词表：`human-review`（人工复核）、`merge-gate`（合并门禁）。构建从资料库 TOPICS 自动注入只读 `topic_vocabulary`，网站直接使用生成数据展示主题选项，不另存第二份词表。主题与标签采用 AND 筛选，清除后恢复全部问题；无结果保留当前筛选并提示清除。列表和详情均展示主题、标签，类型与状态独立展示。

## 网站数据与验证

网站独立读取 GitHub main 的 `questions.json`，首次失败回退随站 JSON，后续失败保留上次成功数据；打开、回前台和每五分钟更新。材料目录继续使用原有 TSV 同步逻辑。localhost 预览问题只读取本地快照，便于验证未推送数据。

若本仓存在 `sites/ai-software-atlas/dist/`，构建同时生成其中的同字节 `questions.json`；`--check-generated` 检查快照一致性。站点是已有的独立 Sites 源仓，未纳入根仓（沿用原来的 `/sites/` 忽略规则）。首次发布页面代码后，日常问题数据变化只需根仓构建和获准推送，网站下一轮读取即可更新。站点再发布前应重新构建更新其随站快照。

```sh
python3 meta/build.py
python3 meta/check.py
python3 -m unittest discover -s meta -p 'test*.py'
node --test sites/ai-software-atlas/test/*.test.mjs
git diff --check
git -C sites/ai-software-atlas diff --check
```

初始化仅含一项实际核读的 GitHub 原文问题；公告能证明产品规则，不能证明治理效果。PACE-Bench 未在本轮追加，静态代码审查不能代替实验证明。

## RSS 订阅

订阅地址：<https://raw.githubusercontent.com/nesnilnehc/ai-era-software/main/feed.xml>。网站可见入口和 head autodiscovery 均指向此真实数据源；不依赖随站静态副本。根仓 build 同时生成 feed.xml，获准推送 main 后订阅地址即可读取最新内容，不需要重新部署网站或新增自动化。GitHub raw 的 HTTP Content-Type 可能为 text/plain，内容为 RSS XML；各阅读器的 MIME 容忍度及更新通知行为须分别验证。

Feed 包含正式资料目录与每个问题的最新实质版本。资料缺少历史收录时间，pubDate 明确使用原文首发日期，描述中区分原文最后更新；月精度使用当月首日编码并注明精度，不能当作本项目新增时间。将来新增资料亦沿用此日期口径，不伪造收录时间。资料 GUID 依据原始 URL 稳定，修正摘要不会伪装成新资料。

问题 pubDate 使用维护记录中的 updated（仅精确到日，RSS 编码统一 UTC 00:00，不声称这是精确操作时刻）。问题 GUID 为稳定问题 ID 加实质内容哈希；问法、方案、主题标签、事实证据或状态变化会产生可预测的新修订身份，仅核读日期、updated、历史说明变化不改变 GUID。Feed 保留每个问题当前最新实质版本，完整历史仍在问题详情；不追溯制造已无内容快照的历史 RSS 事件。阅读器是否提示修订由客户端决定。

lastBuildDate 取条目日期最大值，条目按日期及 GUID 稳定倒序排列；无变化 build 不产生时间抖动。日常维护须遵循无实质变化不空改日期，避免用未来时间置顶。XML 转义、GUID、日期和入口均有回归检查；静态校验不代表全部阅读器实测通过。
